# 007 — Private Media lifecycle and Catalog coordination

Date: 2026-10-05. Status: implemented locally; native/scanner/broker/provider acceptance remains a separate gate.

Media owns immutable file identity, validation, generation selection and delivery. Catalog owns all associations and current public eligibility. No service reads another service's database. Dynamic Catalog Core exists in this checkout and is preserved.

The initial upload profile is bounded server ingestion for both filesystem and S3. Clients transfer exact numbered parts (8 MiB maximum; at most 100) through live ADMIN/Origin/CSRF checks. Part publication and original sealing use write-once opaque keys. Completion records the SHA-256 of the actual sealed stream and queues validation in one SERIALIZABLE Prisma transaction. Streaming/storage calls are outside retries. This trades direct-provider upload throughput for provider-independent enforcement and resumability without asserting untested multipart capabilities. S3 provider-native multipart signing is not advertised.

Allocation reserves staging, original and a maximum initial output generation in a distributed SERIALIZABLE transaction. Idempotency is scoped to the staff ID and a canonical request hash. Reservations survive cancellation, expiry and deletion because retained bytes may still exist; operational inventory is needed before any approved reduction. Repeated transfer capabilities consume bandwidth, so quotas are not a bandwidth guarantee. Repeated failed/regenerated attempts can add retained orphan bytes beyond the initial reservation; attempt tokens are persisted, and operators must monitor provider inventory and stop intake before capacity exhaustion.

PostgreSQL processing jobs are the work authority. Short claims use SKIP LOCKED, a random fencing token, a 120-second lease and a bounded attempt ceiling. Workers renew every 30 seconds. Only the current unexpired lease may select outputs, update readiness and write its event. Separate image/video/PDF lanes prevent long video work consuming every slot. Claim tokens survive in attempt_history for orphan discovery. A failed final attempt after process death is reconciled to an exhausted state. External outputs use attempt-specific keys and remain private if SQL commit fails.

READY requires every configured output plus scanner evidence; emergency security blocking is independent of READY/deletion. Blocked and rejected security states cannot be cleared by this milestone. Regeneration scans the same sealed input and publishes a new complete generation atomically. Failure leaves the prior usable READY generation selected. Small images reuse a generated object across profile aliases, so variant storage identity is now indexed rather than globally unique; asset/profile live uniqueness and immutable generation ownership remain enforced. Old rows and files are retained.

RabbitMQ carries only B5 readiness/security/retirement events from existing service outboxes. Persistent mandatory publications use confirms; consumer acknowledgements follow local inbox/effect commit. Separate producer HMAC keys authenticate envelopes in addition to broker credentials. Quorum delivery limits, backoff and a dead-letter exchange bound failures. Events are at least once; publication confirmation is not Catalog registration confirmation. Unsupported versions and invalid signatures are rejected. Identity and unrelated Catalog outbox events are untouched.

Catalog's existing protected retirement function checks active usage (including private technical evidence) and tombstones the registration in one local transaction. Its durable result drives Media soft deletion. Attachments and authoritative public decisions after that commit fail even if Media's consumer is delayed. Late READY never restores the tombstone. Security projections reject new attachments; Media independently denies fresh delivery immediately after its block commits. Already authorized remote links may remain usable within their existing expiry.

New public authorizations query Catalog's public_asset_usage with an exact owner context. Technical-source DOWNLOAD is separate from raster preview, which remains denied publicly under the present schema. Admin private previews require live ADMIN verification; SUPER_ADMIN has no library capability. Originals are private except explicitly eligible source-PDF downloads. Local streaming checks authorization before HEAD, conditional or range handling. S3 URLs are signed only after a fresh decision, with expiry bounded by both the original Catalog decision and a maximum five-minute Media window. An old URL cannot mint or refresh a grant. Browser caches, active transfers and saved copies cannot be recalled.

Filesystem storage is for an owned private development directory, not public static hosting. It rejects lexical traversal, symbolic links/junctions and substituted file inodes; exclusive hard-link publication prevents replacement. The OS must deny other users mutation of its ancestor directories. Protection against a hostile process sharing the same OS identity is not claimed. Production requires S3 with a reviewed, provider-tested conditional-write/immutable-origin policy, restricted credentials and private origin access. No provider capability is considered verified merely because its API is compatible.

Native parsing runs in child processes with argument arrays, bounded output/time and complete-tree termination. Production Linux requires Bubblewrap with separate network/PID/filesystem namespaces plus deployment CPU/memory/PID/scratch limits; this profile has not been executed on this Windows host. Workers scan before parsing. Unavailability never exposes an unverified original. Known rejected bytes stay in the private retained original namespace with REJECTED security state; the logical quarantine boundary is authorization, not an automatic destructive move.

SQL 16/17 are additive upgrades; 18/19/20 are fresh entrypoints. SQL remains authoritative, including deferred required-output checks, immutable inputs/variants, retained records and Catalog write gates. No application/runtime role acquires migration, DELETE or TRUNCATE permission. No live migration or deployment was performed.

# 006: Dynamic Catalog Core

Accepted locally on 2026-10-04. This separately named milestone follows B4; B5 remains Media core. See [implementation plan](../dynamic-catalog-core-implementation-plan.md), [operating guide](../operations/dynamic-catalog.md) and [model dictionary](../../database/docs/model-dictionary-v1.2.md).

An ordinary product belongs to one active leaf category and one active product type. Categories determine browsing placement; types determine ordinary value eligibility. Technical configurations remain engineering reference contexts, never commercial variants or automatic product values. Category moves preserve the type and values. No inheritance or business-name branching is introduced.

Reusable definitions, options and canonical units retain the existing `specification_*` vocabulary and NUMBER/BOOLEAN/TEXT/CHOICE tables. Seven additive Catalog tables provide types, translations, reusable presentation groups, per-type group placements and assignments, and unit labels. Reviewed SQL controls lifecycle/deferred integrity/grants; Prisma models and transaction-scoped adapters expose these structures through focused ports. Gateway remains without a business database.

Definitions default to private in storage. Public disclosure requires both definition and assignment permission. Search/comparison also require their assignment flags; numeric filtering requires global filterability as well. Global privacy can never be broadened by a type. Public products use a dedicated projection with localized TEXT/CHOICE values and no Admin translation sets or counts. Technical measurement/note queries require global disclosure; notes without a public measurement scope stay private. Explicitly downloadable PDFs are independent: hiding an attribute does not redact file contents, revoke a URL, or change approved evidence. Impact previews report downloadable documents and `fileContentsRedacted: false`.

Each type has an ordinary optimistic version and a monotonically increasing effective `schema_revision`. Changes to the type, memberships, groups, shared definitions/options/units and their translations invalidate affected schemas through indexed reverse dependencies. A revision is an opaque exact string, not an edit count; one transaction can advance it several times. Product/technical-sheet writes do not advance schemas unless a shared definition actually changes. There is no schema cache or business edit-history feature.

Products require current product and schema versions. Configuration changes use read-only impact previews followed by explicit confirmed commits, recomputing the operation/proposal/dependency token inside the same Serializable transaction. A shared change validates all affected active products. Interactive previews are limited to 100 affected types and 1000 active products and reject larger scopes, rather than reporting incomplete safety. Schema/group/assignment collections and complete ordering are limited to 500; options to 500; input values/selections to 100. These are implementation limits, not production capacity claims.

Used type/unit semantics are immutable, including retained deleted values and technical measurements. Unit code/symbol/dimension identity is immutable; label translations can change. Definitions with replacement semantics need new identities and explicit product mappings. Tightened bounds, requiredness, cardinality and lifecycle changes cannot commit an invalid active product. Optional assignment -> explicit value population -> required assignment is the supported staged workflow; no guessed defaults. Deprecation blocks new use, while unchanged legacy values and unrelated edits remain available. Deletion retains all rows and has no restore workflow.

Copying type configuration is a bounded explicit snapshot merge: shared definitions/groups are reused, destination-only memberships remain, differing collision policies block the operation, and memberships/order are independent afterward. Source and destination schema preconditions participate in preview/commit. Product type changes explicitly remove/map incompatible values and validate destination requiredness. Product-specific technical applicability blocks type changes until reviewed through a future technical workflow.

The existing Catalog serialized-writer strategy remains. Prisma interactive Serializable transactions use the private SQL gate indirectly through existing triggers, bounded whole-transaction retries and atomic outbox writes. Domain/application import neither ORM nor transport/environment libraries. External verification/publication is outside retry callbacks. Schema/translation/value reads load relations in batches; no external media calls or mail occur within a Catalog transaction.

Expansion, reviewed mapping, resumable backfill, validation and final switch are separate operator steps. Active mappings are explicit; category names/signatures never decide semantics. Stable assignment IDs derive from mapped type/definition identities. Legacy rows remain but lose eligibility authority at final cutover. Deleted products may retain NULL types. The default v1.1 installation/readiness path remains available; final installation/verification is explicit. New dynamic operations fail with a feature-specific state error before cutover. Real project data was inventoried read-only, not migrated.

Commercial variants, commerce, collections automation, arbitrary rules, tenancy, search engines, Media providers/delivery, broker workers, Inquiry workflows and public/staff/mobile interfaces remain outside this milestone. Branding and gold/silver/bronze requirements remain existing company configuration concerns; locale expansion needs a coordinated contract/database/renderer decision. Existing Arabic/English/Sorani defaults are preserved.

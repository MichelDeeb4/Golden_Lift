# 021 — Permanent deletion of explicitly owned data

Date: 2026-10-08. Status: expansion, application switch and local owner-copy migration implemented; retained-reference compatibility and contraction remain pending.

The deletion request supersedes blanket soft deletion for Products, Media, Attributes, Attribute Groups, Units and Categories. Apply the policy in [deletion-policy](../architecture/deletion-policy.md). Preserve unrelated Identity/Inquiries retention and shared technical documentation.

Catalog accepts intent in a SERIALIZABLE transaction, records a durable operation, removes gallery/cover access and freezes distributed owners. Media processes the existing signed B5 event contract, freezes its asset and removes its complete owned namespaces before removing metadata. Catalog removes remaining owner rows after the completed result commits. Operational rows and inbox/outbox evidence survive for replay. This is eventual completion with a durable unavailable state, not a distributed database transaction.

Direct Media deletion reserves the Media asset version and writes a request to its outbox. Catalog rechecks its own dependency fingerprint before accepting cleanup. A stale or competing request produces a durable rejection and unfreezes the Media asset. Storage failure keeps the accepted operation pending and retryable. Never call another service's repository or perform file/HTTP effects in a retried transaction.

Media writes take an owning-service shared session advisory lock and recheck pending state after acquisition. Cleanup holds the exclusive lock across namespace removal and metadata finalization. A separate bounded four-connection lock pool prevents lock holders from exhausting the transaction pool while awaiting metadata commits; shutdown awaits both storage and lock-session closure. Explicit credential copying preserves PostgreSQL's non-enumerable password property. A real PostgreSQL regression verifies concurrent cleanup through a one-connection transaction pool with explicit runtime credentials. The lock prevents a previously authorized worker from recreating files after successful cleanup. Storage adapters restrict operations to UUID owner namespaces. S3 cleanup includes versions and delete markers; object-lock retention or missing permissions produce retryable failure, not completion.

Reviewed migrations replace physical-delete guards and grants only on explicitly owned business tables. RESTRICT FKs, private SERIALIZABLE write gates, retained evidence and TRUNCATE denial remain. Pending owner assignment guards also reject raw SQL insertion of Products/children into a pending Category. Migration authority stays separate from runtime credentials.

Group deletion computes loss of reachability from the remaining live Groups assigned to each Product's Category. It deletes only values losing their last supplying Group. Attribute deletion removes typed child rows before their parent values. Unit deletion counts all Attribute references, including retained ones, without nulling them. Category deletion checks the full recursive subtree, including historical/pending Products.

The user chose verified independent asset/file copies for every Product/Category owner. Copy original and all retained delivery/quarantine generations to stable target IDs, verify size and SHA-256, then switch Catalog references without changing gallery identity/captions. The manifest is atomically replaced and fsynced; replay verifies existing objects and resumes the same IDs. Source objects and upload-session evidence remain until separately reviewed cleanup. Upload staging belongs to the original upload session rather than the new delivery owner.

Tradeoffs: accepted distributed deletions retain unavailable business rows until cleanup completes; this is necessary to avoid false completion during storage outages. Operations currently bound the request to 1,000 distinct assets, with a 64-KiB signed transport envelope. Existing immutable historical covers, retained technical measurements and retired type assignments require a compatibility decision; impact reports them explicitly instead of failing after confirmation. The dashboard remembers at most 20 operational IDs per staff account in this browser; service endpoints remain the source of status.

Filesystem/PostgreSQL and signed local HTTP checks are current evidence. They do not validate production RabbitMQ, S3, provider retention or scanner acceptance.

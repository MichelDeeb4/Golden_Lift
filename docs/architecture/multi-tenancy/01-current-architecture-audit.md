## Executive finding

Golden Lift has a useful Clean Architecture foundation but is a **single-company system with no implemented tenant isolation**. Inspected Prisma models lack tenant ownership/memberships, actor/event contracts lack tenant context, and reviewed SQL contains no RLS policy definitions. Runtime role creation uses NOBYPASSRLS: a prerequisite, not isolation. Sources: [packages/contracts/src/core.ts:15](../../../packages/contracts/src/core.ts#L15), [packages/contracts/src/core.ts:112](../../../packages/contracts/src/core.ts#L112), [database/scripts/db.mjs:84](../../../database/scripts/db.mjs#L84) and the complete model inventory in [02](02-multi-tenancy-impact-analysis.md).

Adding companies before changing global queries, privileges, relationships and jobs would expose cross-company risk. The present global behavior is consistent with the original single-company scope; this is not evidence of an existing cross-company exploit.

## Clean Architecture, Nest and persistence

Composition constructs adapters/use cases; presentation invokes application ports; application depends on domain/contracts. Nest modules are dynamically composed in the shared HTTP factory using symbol-token injection. Authentication is explicitly invoked, rather than a universal tenant guard/interceptor. Preserve use-case authorization even if transport guards are later added. [packages/platform/src/http.ts:97](../../../packages/platform/src/http.ts#L97); [services/catalog/src/presentation/http/admin-categories-controller.ts:1](../../../services/catalog/src/presentation/http/admin-categories-controller.ts#L1); [services/catalog/src/application/use-cases/authenticate-category-administrator.ts:1](../../../services/catalog/src/application/use-cases/authenticate-category-administrator.ts#L1).

The boundary check passed its static scope; it cannot establish runtime tenant safety. Catalog uses SERIALIZABLE interactive Prisma transactions, tx-bound repository/outbox operations, bounded whole-transaction retries and safe SQL-state mapping. Product management and deletion have separate units of work; Identity uses its own READ COMMITTED/locking strategy. Media uses SERIALIZABLE. ## Identity and authorization

StaffAccounts stores one global ADMIN/SUPER_ADMIN role and globally unique normalized email, without memberships. Sessions/tokens belong to accounts. Roles are deliberately non-hierarchical: SUPER_ADMIN manages Admin accounts; ADMIN manages content. A platform role must not silently become universal tenant content access. [services/identity/prisma/schema.prisma:14](../../../services/identity/prisma/schema.prisma#L14); [services/identity/src/domain/staff.ts:75](../../../services/identity/src/domain/staff.ts#L75); [services/catalog/src/domain/category.ts:16](../../../services/catalog/src/domain/category.ts#L16).

Services authenticate live through internal Identity introspection with service credentials; mutations validate approved Origin and session CSRF. Current actor returns id/role/authVersion only. Gateway forwards a narrow allowlist and shared HTTP strips user/role headers; there is no domain-to-tenant resolution. [services/identity/src/presentation/http/introspection-controller.ts:1](../../../services/identity/src/presentation/http/introspection-controller.ts#L1); [packages/platform/src/staff-auth.ts:1](../../../packages/platform/src/staff-auth.ts#L1); [services/gateway/src/infrastructure/http/staff-proxy.ts:201](../../../services/gateway/src/infrastructure/http/staff-proxy.ts#L201); [packages/platform/src/http.ts:116](../../../packages/platform/src/http.ts#L116).

# Multi-tenancy impact analysis

Date: 2026-10-10. All classifications below are **recommended target ownership**, anchored to verified existing models. None is implemented today. [01](01-current-architecture-audit.md) records the inspection limits.

## Ownership principles

A company is a tenant. A person has one platform identity and zero or more memberships; catalog/media/inquiry records belong to a company. Shared software contracts, UI primitives and supported language definitions are intentionally shared code, not shared writable business data.

Existing Units/Attributes/Groups are mutable, versioned and deletable by content Admins, so classify them as tenant-owned even if names coincide across companies. Optional future starter templates can be immutable platform definitions copied into independent tenant records; no shared writable master catalog is recommended. An asset referenced by Catalog remains owned by Media, with a Catalog projection carrying the same tenant. Cross-service IDs are logical contract references, not cross-database FKs.

## Database and integrity impact

1. **Tenant columns and row identity:** add tenant_id to tenant-owned owners, children, translations, joins, projections, jobs and operational evidence; freeze ownership after migration. Globally unique UUID primary IDs may remain, with unique (tenant_id,id) keys for composite local FKs. Tenant-owned natural primary key Units.code needs deliberate composite-key/client migration; do not assume every table has UUID id.
2. **Same-tenant relationships:** category parent, product/category, both group membership endpoints, definition/options, value/definition/options, product cover-media reservation links and technical provenance chains need tenant-composite FKs. Existing ownership composites (product_id,id), (sheet_id,id), (option_id,definition_id) must retain their old integrity and add tenant identity. Cross-database Media/Identity/Inquiry references are checked via API/events/local projections.
3. **Natural uniqueness:** replace global product model-code reservation code_key, specification/group codes, technical sheet_key, page_key and unit code uniqueness with tenant-qualified equivalents. Preserve global normalized user email and globally unique verified domain names. Existing owner+locale uniqueness can remain mathematically safe with global owner UUIDs, but explicit tenant composites make policy auditable. Keep partial live predicates and reservation/retention semantics; do not start reusing retained codes accidentally.
4. **Singletons:** SiteSettings and NotificationSettings must be tenant-keyed; child settings translations follow their tenant. Catalog.write_gate id=1 must become per-tenant private state before concurrent multi-company writes are accepted.
5. **SQL behavior:** review every SECURITY DEFINER function and live/public/effective view, including retained_deletion_dependencies and exclusive-media-owner validation. Restrict execution/search_path and ensure tenant validation is explicit. Tenant integrity validation must still inspect retained/deferred dependencies within that tenant; do not hide them with live filters merely to pass RLS.
6. **RLS:** tenant equality on reads/deletes and inserts/updates; missing context fails closed. Enable and force RLS where appropriate, retain non-owner NOBYPASSRLS runtime roles, and restrict administrative/background authority. RLS does not replace same-tenant FKs or use-case capability checks.
7. **Query planning:** tenant-leading indexes for roots/ordering, public publication/search/facets, library/status, membership lists, job/outbox claim and pending deletion lookups. Keep trigram/index behavior and verify plans on representative two-tenant fixtures; no benchmark was run here.

## Media-specific impact

- Existing key formats are parsed by FencedStorage. Prefix changes require a shared validated key/ownership strategy across allocate, upload, processor, owner-copy, storage inventory, deletion and recovery. Preserve immutable objects; namespace existing storage through an approved key manifest or verified copy-and-switch, never silently rename files.
- Bind uploader ownership to tenant+user, including idempotency reuse. Scope budgets by tenant without losing the platform-wide storage/job capacity cap or retained reservations.
- Require the same tenant for public host, usage owner, asset/projection and delivery authorization. An ADMIN membership in A must not confer access to B's asset library or upload.
- Signed S3 URLs are bearer capabilities. Bound lifetimes and never cache/log them globally; decide whether suspension permits their remaining lifetime or requires an enforcing delivery proxy.
- Fencing needs tenant-aware metadata lookups on its separate pg pools while preserving advisory locks across file side effects. Do not move long file operations into retried Prisma callbacks.
- Product/Category exclusive-holder policy and independent-copy selection remain binding. Deletion recovery must complete safely while a tenant is suspended or a module is disabled, with narrow operational authorization.

## Preservation and migration obligations

The proposed default is an explicitly approved legacy Golden Lift tenant mapping, not an inference that all unknown future imported data has that owner. Inventory live/deleted rows, retired definitions/bindings, technical observations, ops histories, pending cleanup/jobs and private storage. Every legacy row/event/object must have a proven owner or be reported ambiguous. Pending events may be drained before cutover or translated under a checked legacy manifest; never relabel arbitrary events on arrival.

Preserve Arabic content, exact quantities, inactive drafts/publication rules, unique effective attribute values, reviewed changes, optimistic concurrency, soft-retained unrelated evidence and authorized permanent deletion. No customer interface dependencies allows a coordinated local maintenance cutover; it does not authorize data loss or constraint bypass.

## Required security and regression coverage

Use two unrelated companies with intentionally identical business codes and different content, plus a multi-membership user, tenant-only admins, a revoked membership and platform-only admin. Verify:

- Every public/admin read/write/list/count/search/facet/tree/path/previous-next/impact/status route sees only the resolved tenant; foreign IDs return consistent safe errors.
- Cross-tenant FK inserts/updates, membership joins, option choices, covers, category moves and module actions fail at both application and real PostgreSQL boundaries.
- Pooled Prisma/pg sessions, rollback/commit failures, retries and concurrent tenant requests never inherit a prior context. Missing context fails; read-only sessions and views obey RLS.
- Spoofed tenant/role/Host/forwarded headers, domain mismatch, expired/revoked membership, action-token replay and platform-admin tenant mutation are rejected.
- Direct upload, signed/local delivery, process leases, delayed events, duplicate inbox replay and failed/resumed deletion do not cross tenants or delete surviving files.
- Browser switching cancels old requests, clears scoped private state, handles dirty forms and preserves successful CRUD across reload/read API checks; module disable is enforced at backend as well as navigation.
- Fresh/upgrade schemas preserve retained data/FKs/provenance and maintain Prisma/SQL dictionary parity. Compare pre/post counts and hashes per tenant, not only total row count.

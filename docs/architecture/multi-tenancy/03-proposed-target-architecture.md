# Proposed target architecture

Date: 2026-10-10. Status: **recommendation for approval; not implemented**. Evidence baseline: [01](01-current-architecture-audit.md). Ownership inventory: [02](02-multi-tenancy-impact-analysis.md).

## Decision and rationale

Recommend **shared tenant-qualified tables with PostgreSQL RLS in each existing service database**, one global user identity with tenant memberships, trusted domain/request resolution, and explicit tenant-aware application ports. Keep Identity, Catalog, Media and Inquiries ownership separate; keep Gateway stateless. Introduce no new service and no inventory implementation.

The concrete problem is global company data/permissions in an otherwise modular system. Existing tx-bound Prisma repositories, reviewed SQL and runtime/owner roles make shared-table isolation a practical extension. Its cost is substantial SQL and access-path review; it is not a cheap tenant filter patch. This choice should be recorded as an approved ADR under the established documentation/decisions location when implementation is authorized; this proposed decision remains here to avoid editing existing architecture documents.

## Tenant storage alternatives

| Option              | Benefits                                                                                                                                                   | Costs for this repository                                                                                                                                                                                                 | Verdict                                                                                                    |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Shared tables + RLS | One schema/client/migration stream per service; tenant-local relationships and efficient pooled operations; small-company onboarding needs no new database | Every business table/function/view/read/job needs isolation review; tenant restores/large noisy neighbors require care; shared runtime credential compromise is a broad risk                                              | Recommended for initial small-company platform with application authorization + RLS + tenant-composite FKs |
| Schema per tenant   | Namespace separates tables; potential tenant exports                                                                                                       | Four services multiply tenant schemas/migration/trigger/grant work; current Prisma schema mappings are service-static; safe dynamic schema selection, search_path, pools and generated client strategy need new machinery | No demonstrated requirement justifies this operational burden; namespaces alone do not authorize selection |
| Database per tenant | Stronger database/credential blast-radius isolation; tenant-specific backup/restore/lifecycle                                                              | Four databases per company plus connections, provisioning, migrations and relays; platform identity and routing still needed; service config currently assumes fixed runtime roles/URLs                                   | Reserve for future contractual isolation/compliance or large customers, not the initial default            |

These are architecture tradeoffs inferred from inspected service schemas, SQL, composition and config, not performance measurements. PostgreSQL documents default-deny enabled RLS, owner/BYPASSRLS exceptions and referential integrity behavior: [Row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html). RLS supplements trusted application context; it does not solve storage or messaging authorization.

## Service topology: retain versus simplify

A modular monolith with one process/database could reduce local orchestration, deploy/retry complexity and cross-service calls. It would also require deliberate ownership, schema/client, startup and distributed deletion migration; it cannot be accomplished by importing another service's repositories. Standing project rules require separate service databases. Replatforming and tenancy together would increase review scope with no measured operational benefit.

Chosen approach: retain boundaries, allow one managed PostgreSQL instance with separate databases/roles, one ingress and coordinated release tooling. Keep existing workers separate from HTTP processes for isolation. Inquiries has only foundational workflows; do not build new Inquiry features just to justify its process. Reconsider topology later only after operational measurements and an explicitly approved architecture change. ## Module ownership

| Boundary                       | Owns                                                                                                                                                 | Does not own                                                 |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Identity: access/control plane | Platform users/credentials, tenant lifecycle, verified domains, memberships, platform roles, tenant roles/capabilities, module activation/version    | Catalog business definitions, inventory records, Media bytes |
| Catalog                        | Tenant products/categories/configuration/typed values, company site content/branding/language policy, technical evidence and Media usage projections | Authentication credentials or other service tables           |
| Media                          | Tenant uploads/assets/variants/storage/jobs/quotas, delivery and cleanup                                                                             | Product/category business ownership decisions                |
| Inquiries                      | Tenant inquiries/snapshots/notification settings and future workflows when separately authorized                                                     | Catalog DB joins or Identity credentials                     |
| Gateway                        | Routing/resolution adapter, HTTP contract aggregation, safe authenticated context forwarding                                                         | Tenant business persistence or arbitrary header authority    |
| Frontend                       | One app shell, reusable catalog/staff UI and module navigation from server config                                                                    | Authoritative permission/module decisions                    |

Tenant registry is a focused Identity module because lifecycle/domains/membership already meet its access responsibilities. Identity holds only activation metadata, not each module's business rules. Shared platform holds technical context transport/transaction helpers; contracts hold dependency-free IDs and validated context/event shapes. Neither becomes a generic business service locator.

## Identity and tenant lifecycle

Recommended new models in Identity:

- **Tenant:** immutable UUID, stable key, display name, lifecycle status/version and timestamps. Start with PROVISIONING, ACTIVE and SUSPENDED; onboarding failure is recoverable. Archived/offboarding states require an approved retention/export procedure; suspension never deletes data.
- **TenantDomain:** tenant ID, normalized hostname, verification/status/version, purpose (public/admin where needed). Hostnames are globally reserved and unique with controlled reassignment; prove DNS control before custom-domain activation. Do not accept a tenant ID supplied by DNS/host without registry validation.
- **TenantMembership:** tenant ID + global user ID, role, status, membership/auth version. One membership per user/company; invitations target that pair. Revoking membership affects that company's access, not the same person's other memberships.
- **TenantModule:** tenant ID + known module key, enabled/status/version. Initially catalog and its required Media capability; inquiries stays unavailable until implemented. Inventory is not enabled just because it is a known future concept.
- **Platform role association:** explicit platform_admin privilege separate from tenant memberships. Start with a small fixed tenant role-to-capability policy (tenant_admin/content_editor if justified), not an arbitrary permission-builder UI.

Reuse the existing StaffAccounts credential/session/token mechanisms through an approved migration to platform-user semantics; do not create competing login tables. Preserve normalized global email uniqueness and account-wide authVersion for password/account changes. Add membership version/status to tenant authorization. A reset token remains account-scoped; a membership invitation is tenant-scoped and cannot grant platform privileges. Existing SUPER_ADMIN maps to platform account/tenant administration after explicit review; existing ADMIN maps to approved legacy-company membership, not all companies. Sources: [services/identity/prisma/schema.prisma:1](../../../services/identity/prisma/schema.prisma#L1), [services/identity/src/application/use-cases/action-tokens.ts:1](../../../services/identity/src/application/use-cases/action-tokens.ts#L1), [services/identity/src/domain/staff.ts:1](../../../services/identity/src/domain/staff.ts#L1).

Provisioning is idempotent: Identity records intent, owning services initialize local tenant policy/config through authenticated contracts, acknowledgements/version state are recorded, and tenant becomes ACTIVE only when required readiness is satisfied. No cross-database transaction/FK; use existing outbox patterns where applicable. Failures remain PROVISIONING with a safe retry, not a partially usable tenant.

## Domain and authenticated tenant resolution

1. Ingress terminates TLS and normalizes host/port against a verified TenantDomain registry. Trust forwarded-host/proto only from configured proxy hops. Unknown/unverified/suspended domains fail closed; never default to Golden Lift.
2. Public requests obtain an authoritative ACTIVE tenant resolution. Initially resolve/check through Identity per request; Gateway may deduplicate within a request but not introduce an indefinite cache. Short caching later requires explicit bounded-staleness rules for suspension/domain reassignment.
3. Staff authenticate with the existing opaque live session. Selected tenant from a server-resolved tenant host or explicit central-admin route is a **selector**, never authority. Identity verifies membership/status/capabilities and module state for that tenant. Host and selector must agree where both exist.
4. Gateway forwards a versioned authenticated internal context over existing service trust with integrity bound to tenant, audience and expiry/request where appropriate. Drop client tenant/user/role headers. Owning services validate ingress context; protected services additionally call live Identity introspection for tenant membership/module authorization. Direct external service calls must not accept self-asserted context.
5. Application inputs explicitly carry TenantContext / TenantActor. Domain/application receive values and policies through contracts/ports; no environment, HTTP, AsyncLocalStorage or Nest Request lookup. Logs may use infrastructure request context, but repository authority remains explicit.
6. Public tenant scope includes Catalog and Media usage authorization. Service-to-service calls propagate validated tenant and expected policy version; background jobs use authenticated operational context with recorded tenant, not an arbitrary synthetic ADMIN.

Suggested context fields: tenantId, tenantVersion, capability/module policy version; protected actor adds userId, membershipId/version and approved capabilities. Platform operations use a distinct platform actor/context. Do not overload a null tenant to mean unrestricted administrator access. The platform host's host-only cookie never needs to be shared with tenant domains. Cross-host login/SSO is deferred unless specifically required; no broad cookie Domain or wildcard credentialed CORS. Change upload instruction/client routing deliberately rather than letting the current MEDIA_PUBLIC_ORIGIN workaround become the tenant design. ## Prisma and PostgreSQL access strategy

Every tenant data operation, **including reads**, enters an owning-service scoped query/transaction session. Existing UoWs accept explicit context and initialize it on the Prisma interactive transaction client before repositories/outbox run. Use parameterized transaction-local set_config('app.tenant_id', tenantId, true), not a session SET on a pooled root client. On retries initialize context again. Preserve each service's isolation, timeout and error mapping. This uses Prisma interactive transactions already present; [Prisma transactions](https://www.prisma.io/docs/orm/fundamentals/transactions) describes their callback/client behavior, and PostgreSQL's [configuration functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-SET) define the local setting scope.

Repository filters explicitly include tenant for clarity and early errors; database RLS is a second boundary. For tenant-owned rows, policy compares tenant_id with the trusted transaction setting, with both USING and WITH CHECK. Missing/empty context denies access (or a controlled error); tenant IDs are immutable. Keep non-owner NOSUPERUSER/NOBYPASSRLS runtime roles; FORCE RLS where needed and test actual roles. No blanket platform-admin bypass policy. RLS is not protection from arbitrary code execution/SQL injection under a shared runtime credential that can set context, so authenticated context, parameterized SQL and restricted function grants remain essential.

Retain global UUID IDs and add local unique (tenant_id,id) plus tenant-qualified composite FKs. Move natural keys such as Units.code and business code reservations to tenant-qualified identity without changing bigint/decimal handling. Tenant registry projections in each owning DB provide local tenant/policy references; they are versioned read models, not independently writable sources of truth. Identity is lifecycle authority; local projections cannot override suspension checks. Use privileged deployment credentials only for reviewed DDL/backfill, never HTTP runtime.

Rewrite/review live/public/effective views for caller-context security (security_invoker where supported) and explicit tenant joins. Review SECURITY DEFINER functions individually for caller tenant checks, safe search_path, restricted execution and FORCE RLS effects. Retained-data scanners may need narrowly privileged operations that return only tenant-local blockers. Do not grant runtime ownership or bypass just because a deferred trigger fails. Preserve validation of hidden retained rows through the owning integrity policy.

Replace global write_gate with one private row per tenant and tenant-scoped revision/validation. Start by preserving the correctness-first gate pattern within each tenant; optimize only after lock/retry measurements. Deferred triggers, root category ordering, schema revisions, fingerprints and pending-delete uniqueness all bind tenant.

Special case: FencedStorage holds session advisory locks across external file writes and uses another pg pool. Supply explicit tenant-scoped metadata access via bounded short transactions on those connections, reset local settings on end, retain/destroy connections safely on errors, and hold the existing lock outside retried file effects. No database work may bypass context just because it is an operational adapter. Sources: [services/catalog/src/infrastructure/prisma/unit-of-work.ts:1](../../../services/catalog/src/infrastructure/prisma/unit-of-work.ts#L1), [database/sql/05_catalog_integrity.sql:1](../../../database/sql/05_catalog_integrity.sql#L1), [services/media/src/infrastructure/storage/fenced.ts:1](../../../services/media/src/infrastructure/storage/fenced.ts#L1).

## Workers, events and operational authority

Version tenant business event envelopes; require tenant identity, producer, aggregate identity/version and correlation. Use explicit PLATFORM scope for platform security/control events rather than fake company ownership. The strict existing v1 schema cannot silently accept new fields. Update JSON schemas and producer/consumer validators, then drain/translate legacy events with a reviewed mapping.

Keep current shared service queues/outbox relays initially. Narrow discovery authority may list lease metadata (tenant/job/event IDs) across tenants, but must not expose arbitrary business tables. Worker loads/claims/applies under that tenant in a short transaction, revalidates job/entity/lease, and fences output publication. Add per-tenant concurrency/resource budgets plus platform caps to prevent starvation. Inbox dedup/aggregate ordering are tenant-qualified where required; globally unique event IDs may remain globally unique.

Normal content/new processing pauses on suspension/module disable. Already accepted cleanup/reconciliation continues with narrowly scoped operational permission, because leaving bytes half-deleted is unsafe. Outbox publication/retries should continue for durable completed operations. Redelivery after tenant suspension must follow explicit operation policy, not replay as an active tenant admin. Keep external HTTP/mail/file operations outside transaction retry callbacks. ## Media, language, branding and modules

Use tenant-owned storage namespaces for new objects and a validated manifest for preserved legacy keys. Namespace originals, staging, generations, quarantine and owner copies consistently. Do not deduplicate customer files across tenant ownership. Prefix is operational isolation, not authorization; Media metadata, usage owner and resolved tenant must agree. Same-origin upload/delivery routing preserves host-only staff cookies. Retain scanner security, immutable publication, version-aware deletion and restricted PDF source rules.

Catalog owns tenant site content/brand/language settings; expose safe public configuration through Gateway. Identity owns domain/lifecycle/module authority. Catalog maintains a versioned local policy when SQL needs default language; local metadata/provisioning may not alter Identity lifecycle. Initially allow tenant default/enabled subsets of the existing ar/en/ckb support. New arbitrary languages are separate scope. Move required-name/fallback policy from literal ar to approved tenant default across SQL, domain, response projection and forms. Reject unsafe default-language changes until all required content exists; existing Golden Lift content keeps Arabic default.

Module activation is enforced inside owning use cases as well as presentation/navigation. Catalog requires Media for current publication rules; a platform change cannot disable dependencies while active features rely on them. Disabling a module preserves data, denies normal use, and leaves recovery/export/cleanup as explicit operational cases. Do not expose unimplemented Inquiry or Inventory actions merely because a registry key exists.

## Frontend target

Extend one app and its existing shared UI/data ports. Bootstrap server-verified TenantConfig before public queries. Central staff UI lists current memberships and selects a tenant; platform pages have separate capabilities/routes. Public query keys include tenantId, locale, normalized filters and source; private keys include tenant and relevant actor/authorization scope. Media URL grants, deletion history, persisted locale and drafts are partitioned too.

On tenant switch: apply existing dirty-form dialog, cancel outstanding old queries/mutations when safe, reject late results using captured context, reset private client/CSRF/membership state, and fetch the newly selected context. Each mutation captures its original tenant; it must not write to whichever tenant is currently selected at response time. Preserve URL pagination/filter context per tenant and targeted invalidation; no full reload as CRUD strategy.

Parameterize brand/header/footer/titles/mail/template copy/theme within validated configuration; keep platform design primitives/accessibility/RTL consistent. Treat existing web-only admin APIs explicitly; native tenant selection/deep-link resolution can reuse contracts later without claiming native workflows are completed.

## Future inventory seam and migration impact

Future inventory is a cohesive bounded module with its own stock/reservation policies and persistence ownership, tenant-scoped product references through Catalog API/events, and independent permissions/activation. Do not put stock counts on current Products merely for future readiness. Decide whether inventory deserves a service only when its transactions/operational requirements exist. No inventory models, routes, workers or UI are proposed for immediate implementation.

Migration follows expand → approved owner backfill/manifest → switch every caller → real two-tenant verification → contract obsolete global paths. Pre-production allows coordinated maintenance with backups and paused writers/workers, avoiding speculative zero-downtime complexity. Data preservation, live authorization, deletion recovery and complete schema parity remain mandatory.
